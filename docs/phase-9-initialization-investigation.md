No raw response body, headers, API key, card information or authorization object was printed or stored.

The diagnostic's `authoritative.transactionFound=null` means its normal verified-transaction DTO was not established. The separate HTTP status/allowlisted not-found category records the actual provider lookup result; it must not be confused with a timeout or lack of response during this later GET.

## Traced initialization failure

1. The booking's saved amount was passed to the existing test initializer. Its local attempt was created as `initializing`.
2. The adapter validates the local test-mode/key gates, callback origin and actual database identity before its fixed-host request. A direct execution of the actual database-identity guard now passed, without making a provider request. This establishes the guard's current result, not a historical trace of the first request.
3. The request uses a **10-second AbortSignal timeout**, rejects HTTP redirects and rejects non-2xx responses, malformed/oversize JSON and unsuccessful provider envelopes.
4. After a successful initialization response, it requires a matching reference and an HTTPS `checkout.paystack.com` URL, with no userinfo or nondefault port. A missing URL or an unexpected origin also rejects the response.
5. All request exceptions are replaced with the same generic service-unavailable exception. The surrounding initializer catches every provider initialization exception, saves no checkout URL and writes `pending` / `initialization_uncertain`.
6. The persisted attempt changed from creation to its last update after **10 recorded seconds**. That matches the configured timeout and supports a timeout explanation, but cannot identify whether DNS, TCP/TLS, provider latency, body reading or another delayed failure caused the original exception. A response/validation failure near that limit cannot be excluded.
7. The stored event source `provider` and event status `pending` are generated by the local code even when initialization throws. They are not proof of a Paystack response or an authoritative Paystack pending transaction. No original HTTP status, network error code, timeout-stage diagnostic or URL-rejection reason was retained.

**Conclusion:** a request timeout is consistent with the timing evidence; the exact original cause remains unproven. The later successful HTTP exchange shows the verification endpoint was reachable for that GET, not that the earlier initialization network path was healthy. There is no evidence sufficient to blame keys, fictional email, callback settings, metadata encoding or checkout URL validation specifically. Do not relax checks or retry initialization based on a guess.

## Confirmed code defect and proposed correction — not applied

The confirmed defect is **loss of sanitized failure classification**: database guard, HTTP rejection, network/timeout, response parsing, reference mismatch and checkout URL rejection all become indistinguishable. This is a diagnostic defect; it is not evidence that the accounting safeguards or HTTPS allowlist are wrong.

Proposed correction for review:

- Introduce a typed internal provider failure carrying an allowlisted stage/category, HTTP status when present, elapsed time and a small allowlist of network/TLS codes.
- Keep generic guest messages, strict test gating and HTTPS/reference validation. Never retain raw provider bodies, URLs/access codes, headers, keys, card/authorization fields or raw exception messages.
- Preserve the unresolved attempt and full accounting behavior on uncertainty. Do not automatically retry initialization, extend timeouts, create another reference, clear the active attempt, post a payment or mark the booking failed/paid.
- Decide separately whether sanitized diagnostics belong in process logs or persistent audit events. Persistent updates would need explicit approval before application to this existing attempt.

No production adapter/service/accounting code was changed in this investigation. The proposed correction has not been deployed or used to make another initialization request. A further checkout still requires separate owner approval.
